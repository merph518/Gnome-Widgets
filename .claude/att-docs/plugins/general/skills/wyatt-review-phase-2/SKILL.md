# Wyatt Review, Phase 2

`/wyatt-review-phase-2 <n>`, where `<n>` is the pull request number.

The author is a junior engineer. The number is the reference pull request in this repository
of one of the author's pull requests on the work side. Ask for it when it is missing.

## What it does, and how it differs from the first round

`<phase-1-skill>` is the first round: it proves each fix on a throwaway branch, deletes that
branch, and leaves one teaching comment per finding for the author to apply themselves. This
skill is the second round. It makes the fixes itself and explains how each was made, in the
same teaching voice, so the author reads what was fixed and why and applies nothing.

Some of the code under review was generated by an assistant and is intricate enough that the
author cannot be expected to fully understand how to fix it. A review that goes back and forth
while they stumble through it is not productive. So this round fixes every outstanding mistake
in one pass, and the write-up explains what was wrong, what changed, and why, so they can
follow and learn from it. The write-up:

- does not assume they could reproduce the fix;
- says in a plain sentence which parts are intricate;
- never ends with a task for them.

The scope rule: fix all outstanding findings that hold up, not a sample, so a third round is
not needed. A finding that needs the author's product knowledge, or the user's call, goes to
the user per `<asking-note>` (see section 5).

The review itself is identical: effort high, no finding cap, each finding checked against the
author's code, `<review-context-docs>`, and the repository lint rules. That method is in
`<mentoring-notes>` and is not repeated here.

## Nothing is sent

This skill sends nothing to the author or to the work side. Hard stops:

- no sync or review route to the work side, no push to the work side, and no comment posted
  through it;
- no comments on any pull request, and no approval or request for changes;
- no pull request for the fix branch, and no push to their branch; the only pushes are the new
  fix branch in section 7 and the new docs branch in section 8, both plain pushes, and the one
  pull request this skill opens is the docs pull request to the default branch;
- no force-push and no rewriting of pushed history;
- no merge;
- nothing named in `<hard-stops>`.

The one work-side call it makes is the read in section 2, which writes nothing.

The user reads the wiki pull request, decides about the fix branch, and says send, per
`<send-ask>`. The sending is a separate ask.

## 1. Confirm the pull request

```bash
gh pr view <n> --json number,title,headRefName,headRefOid,state,commits
```

Read the commit authors' names in `commits` to confirm the work is the author's, and say which
pull request is being worked. `headRefOid` is the commit every finding is verified against and
the fix branch starts from.

Find the work-side pull request it mirrors, `<work>`, which names the page, per
`<work-side-lookup>`. When no pair is recorded, ask the user for the number per
`<asking-note>`.

## 2. Read what the first round told the author

The first round's comments are a script: each one told the author what to change and showed the
code to write. This round checks that the author followed it, and that what they wrote does not
break anything. Read every thread on the work-side pull request, with the author's replies, per
`<work-side-threads>`.

Then read the first round's reviews on the reference pull request here too, since a finding
the first round left in its summary body, or a comment never sent across, is not on the work
side:

```bash
gh api repos/{owner}/{repo}/pulls/<n>/reviews --paginate --jq '.[]'
gh api repos/{owner}/{repo}/pulls/<n>/comments --paginate --jq '.[]'
```

Count each finding once, from its work-side thread when it has one, since that thread holds
their replies. An inline comment here that went across has a work-side thread on the same file
and line opening with the same bold claim: match it that way and keep only the work-side
thread. A review body never crosses, so a finding in one is counted from here. Issue comments
carrying a marker from `<mirror-markers>` are copies of work-side threads and are not read at
all.

Skip system threads (votes, policy, pushes). For each thread a reviewer started, and each
finding in a review body, record in a table in `<scratch-dir>`:

- the file and line it anchors to, and its bold claim;
- the fix it told them to make, with the code it showed;
- their replies, and the thread's status;
- on their head commit, whether the fix is in: **followed**, **partly followed**, **not
  followed**, or **settled another way** (their reply gives a reason the reviewer accepted, or
  the code was removed).

Every thread that is not followed or only partly followed is a finding in section 4, marked as
advice they already had. A thread they followed still gets read in section 4: the review checks
that their version of the fix works and did not break the lines around it, and a fix that broke
something is a finding too.

## 3. Cut the scratch worktree and the fix branch

Build the fix branch in a worktree in `<scratch-dir>`, per `<fix-branch-form>`.

First choose `<round>`, which names the fix branch, the docs branch and the page, per
`<round-names>`. Take the first name that is unused in all four places, since a branch or a
page can survive on its own after the others are gone:

```bash
git ls-remote origin refs/heads/<fix-branch> refs/heads/<docs-branch>
gh pr list --state all --head <fix-branch>
gh pr list --state all --head <docs-branch>
git cat-file -e origin/<default-branch>:<page>
```

A round is unused when the first command prints nothing, both `gh pr list` calls print
nothing, and the last command fails because the page is not on the default branch. The fix
branch, the docs branch and the page always carry the same `<round>`.

```bash
git fetch origin pull/<n>/head
git worktree add -b <fix-branch> <dir> FETCH_HEAD
```

Link dependencies into the worktree as `<fix-branch-form>` says. All fix work happens in that
worktree. Section 7 removes it and leaves the branch in place.

## 4. Find and verify the findings

Per "Finding and verifying findings" in `<mentoring-notes>`, with these additions:

- Read `<review-context-docs>`.
- Run the type and lint commands from `<static-checks>` on the changed files in the scratch
  worktree, so a claim about types or lint is settled by a run.
- A red check caused by the author's branch being behind the default branch is not a finding
  and not fixed here. It becomes one line in the write-up summary.

Drop what does not hold up, and record why for the report.

## 5. Fix one finding per commit

Make each fix in the scratch worktree and commit it alone. A commit message says what the test
asserted before and after. Follow `<fix-rules>`.

A fix never weakens what a test asserts. It must not:

- remove, loosen, or reorder an assertion;
- change an expected value to match what the application showed;
- skip a test or mark it as expected to fail;
- raise a wait beyond the repository's named limits;
- swallow an error;
- delete a test or step, or change its identifier.

`<fix-rules>` adds the repository's own forms of these rules.

Ask the user per `<asking-note>`, not in text, when a finding is a judgment call: two readings
of a spec, a check that would change, shared code with callers outside the author's files, or
anything needing product knowledge. If the user declines a fix, drop that finding and report
it in the final report only; the write-up does not mention it.

Comments, skip reasons, and log strings written by a fix describe how the code works now, per
`<text-rules>`.

## 6. Check each fix

Before each commit, in the scratch worktree, run the static checks from `<static-checks>`, or
the type and lint commands on the changed files. This skill dispatches no test runs and does no
baseline run. The write-up says plainly which fixes were verified statically only and, where a
fix changes what a test does at run time, that the run is left to the user.

## 7. Push the fix branch and remove the scratch worktree

```bash
git push -u origin <fix-branch>
git worktree remove <dir>
```

The push is a plain push of a new branch. Never force it, and never push to their branch. The
worktree is removed and the branch stays.

## 8. Write the wiki page and open its pull request

The write-up is a wiki page. Merging its pull request is what publishes it, so the user reviews
it as a pull request first.

Create its branch from the default branch and enter it, per `<docs-branch-flow>`. From here the
work follows the implement procedure from its worktree step on: the self review, the ready
signal, and the pull request to the default branch.

The page lives at `<page-location>`, one page per round, with `<round>` as chosen in section 3.
When `<page-index>` has no row for the folder, add it first, then write the page, then run the
generator so the folder page and its order file are built. If another open pull request already
adds the row, ask the user per `<asking-note>` whether to wait for that one to merge or to add
the row here too.

The page holds, first, a short summary: the pull request, the findings fixed, how many of them
the first review had already told the author how to fix, and one line per red check caused by
the author's branch being behind the default branch. Findings that did not hold up, and
findings the user declined, are left out of the page entirely, from the counts too, and appear
only in the final report. The summary is not a teaching section. Then, per fix:

1. A bold one-line finding. When section 2 found the first review already told them how to fix
   it, the next line says so in a sentence: what that comment told them to do, and what the
   code does instead (not done, done in part, or done in a way that broke something).
2. What kind of problem it is and why it matters.
3. What went wrong as the code stood.
4. The background they need, read from the source first.
5. How it was fixed, in numbered steps, past tense ("here is how I fixed it"), written so they
   understand the reasoning, not so they can copy it. A plain sentence names the parts that are
   intricate.
6. BEFORE and AFTER code, each in a fenced block.
7. How to tell it worked.

The voice, and the background to explain, are in `<mentoring-notes>`. The page ends with no
task for them. No commit hashes and no branch names go in the page text, since neither exists
on the work side.

Before the commit, run `<page-gates>`, and scan again after any edit. Never invent an expansion
for a short form; every one is defined in the dictionary `<page-gates>` names.

## 9. Report back

Tell the user:

- the fix branch name and what it holds, one line per commit;
- the wiki pull request;
- findings kept and dropped, a line each, with why for the dropped;
- the first round's threads, a line each: followed, partly followed, not followed, or settled
  another way;
- the stale-base lines;
- what was not run: the fixes were checked statically only, and any run left to the user;
- what the user does next: read the page's pull request, decide on the fix branch, and say
  send. The skill sends nothing.
